-----------------------------------------------Lecture 3
	
Docker Multi stage build : In Traditional DockerFile Image, it contains Maven, JDK, Build Tools, Source Code and Image size become 1-2 GB due to which PULL and Push 
							become Slow.
							
							Multi-stage build lets you use one image to build the app and another to run it. 
							You copy only the final artifact (JAR, binary, etc.) into the runtime image.
	
Example:
		
		DockerFile
			
			# Stage 1: Build
			FROM maven:3.9-eclipse-temurin-17 AS builder
			WORKDIR /app
			COPY pom.xml .
			RUN mvn dependency:go-offline
			COPY src ./src
			RUN mvn package -DskipTests
			
			# Stage 2: Runtime
			FROM eclipse-temurin:17-jre-alpine
			WORKDIR /app
			COPY --from=builder /app/target/app.jar app.jar
			CMD ["java","-jar","app.jar"]
			
		We have two stages of Dockerfile, in above code, we will copy or take only those things from stage 1 that is required in stage 2
		
		COPY --from=builder /app/target/app.jar /app/app.jar                //It copies app.jar from another build stage named builder into the current image.
		No source code copied
		No build tools copied
		Only the final JAR file
		
		
		| Part                  | Meaning                                |
		| --------------------- | -------------------------------------- |
		| `--from=builder`      | Copy from **builder stage**, not local |
		| `/app/target/app.jar` | Source path inside builder             |
		| `app.jar`             | Destination → `/app/app.jar`           |

-----------Master Node Components	

Master and Worker Nodes:  These are the Virtual Machines, on master node we will have configured our Kubernetes  and on worker nodes we 
							will have application configured running on containers.
							For making any node as worker node, we need to join the worker node with master node.
				
Master Node have many Components running, which is acutually orchestrate the whole container management process.
The worker nodes have running application containers
The Containers in worker nodes are encapsulate under a logical component called POD. This POD actually helps to run a container.
The POD can have one or more containers.

			
API Server on master node is the centre of control plane, means any incoming request from client first reach to API Server and than APIServer will communicate with other
components on its behalf
API Server (kube-apiserver) is the central communication point of the Kubernetes cluster.

Schedular decide the suitable worker node to run POD by checking some parameters like CPU, Available memory, Storage.
Kubernetes Scheduler decides on which Node (VM) a Pod should run

Controller Manager Continuously monitor the cluster and make the actual state match the desired state. It consist of Objects like Node controller, namespace Controller, deployment controller  etc.
it make sure that all the controller are running fine. These controller keep monitors the object running on worker nodes like if POD on any of the worker nodes goes down than
POD corresponding controller will restart that POD.

ETCD is a distributed key–value database that stores the entire state of a Kubernetes cluster. Everything Kubernetes needs to remember:
Which pods are running
Which nodes exist
Which containers should be running
Current + desired state
Deployments & ReplicaSets and ETC

ETCD Runs on control plane (master) nodes, but can be configured External cluster (recommended for production)
Kubernetes works on this idea: Desired state ≠ current state → reconcile using ETCD (etcd is the source of truth.)

Note : If ETCD goes down than, Existing pods keep running we cannot Create pods, scale the deployment
		If etcd data lost Kubernetes loses entire cluster state, Cluster becomes unusable means If the notebook is lost: Workers keep doing current tasks But no new instructions can be written
		

Controller Manager : If etcd is the memory, then Controller Manager is the decision-maker that acts on that memory.
					Controller Manager runs controllers that continuously watch the cluster state and make changes to move it toward the desired state.
Type:
	Node Controller : detects the nodes failure, mark it as not ready and evict the PODS from dead node.
	ReplicaSet Controller : Ensures correct number of pods, Creates or deletes pods as needed
	Deployment Controller: Manages rolling updates, Handles rollbacks
	Job Controller: Ensures batch jobs complete, Restart failed job if needed.
	Endpoint Controller: Keeps Service endpoints updated
	Namespace Controller: Cleans up resources when namespace is deleted


 
--------------------------Worker Node Components
			
Kubelet: it receives the instructions from master node via APIServer to Manage the PODS, like create POD, Delete POD etc and it has to follow the instruction.


Kube-Proxy: Every Worker node have one Kube-proxy. 
			kube-proxy decides how traffic reaches that pod. it allows the PODs to communicate with each other.
			kube-proxy enables network communication to Kubernetes Services by routing traffic to the correct Pods.
			Container does not have any its own IP, it communicate via PODS, PODs have IP which is shared by all the container under that POD
			Every Worker Node have PODS, and PODs are ephemeral it get change on every restart or recreation after delete, So IP changes but client needs a stable IP
			KUBE-PROXY implements the networking Service on top of PODs using iptables/IPVS rules
			


------------------------Work Flow

Kubectl is a command line that allow to communicate with kubernetes cluster, 
	1. Command hits on kubectl master node, first reaches on APIServer.
	2. APIServer First Authenticate the request and send the request to ETCD DB, 
	   here ETCD will not create the POD it will make an entry for creation of POD.
	3. After Entry creation in ETCD APIServer will send the request to schedular to schedule a healthy node for POD.
	4. Now Scheduler will connect to worker node through API server and finds that which node is healthy, where a new pod can be create.
	5. Now scheduler will tell APIServer after taking a decision that I found a healthy node, go and schedule the POD on this node.
	6. Now APIServer will reach out to kubelet of that specific node (hey I have Job for you, schedule this POD on your node), 
	   Kubelet will create POD and send the detail back to API Server, APIServer will ask ETCD to make the entry in ETCD DB that POD has been created successfully, and send the details back to user

Note : Whenever user hit the command to fetch any information from cluster than APIServer will directly fetch it from ETCD DB, no need to go through complete cluster.

A Pod is the smallest deployable unit in Kubernetes. It runs one or more containers.
You can create one or multiple container in a Pod and run your application inside it.

But here’s the problem with using Pods directly
	No auto-restart if it crashes
	No scaling
	Not self-healing in a robust way   etc.

In real-world Kubernetes usage, you don’t create Pods directly. Instead, you use higher-level controllers:
Kubernetes provides controllers to manage the PODs
Example: Replicaset, Statefulset, Daemonset, Job/CronJob etc.

Deployment and Replicaset

Replicaset : Deployment is a higher-level controller object used to manage and maintain Pods. POD created under ReplicaSet

: let we have a pod running on a worker node, and suddenly the pod crashes due to any reason than?? to prevant that we should have a mechanism which restore 
	the POD immediately. kubernetes have replication controller(older version) and replicaset that is new version, which take care of restoration.
	and also for high availability it take cares.
	
Example:
				
				User  --->   Replication Controller or ReplicaSet   -->  POD
			
When we declare Replicaset than POD will create under ReplicaSet and replicaset will manitain the number of POD replica under neith.
Here RC is also acting like a load balancer.
If no capacity is available on current node, than it will spin a new pod on new node which is available.


Note : As we discussed earlier that POD will get create under RC, so under the below configuration of RC we will put the configuration of POD.


Create RC.yml
	
	apiVersion: v1									//this we can get using command :  kubectl explain rc
	kind: ReplicationController						//this we can get using command :  kubectl explain rc
	metadata:
	  name:nginx-rc
	  labels:
	    env:demo
	spec:
	  template:
	    metadata: 
		  labels:
		    env: test
		spec:
		  containers:
		  - image: nginx:latest
		    name: nginx
	  replicas: 3
		
	  
	Run  Command: kubectl apply -f RC.yml

-----------------------------------------------------Lecture 14
Taints and Tolerations: Taints and Tolerations are a mechanism in Kubernetes used to control which Pods can be scheduled on which Nodes.

Taint = Node says "Keep away!"  Do NOT schedule any new Pods onto this node unless they explicitly tolerate this taint." (Kind of reservation)
Toleration = Pod says "I'm allowed here."

Let we have three nodes
worker-node1
worker-node2
worker-node3

and Worker-3 is a powerful machine with 64 CPUs and 256GB Ram and we want only database Pods to run on Worker-3.	
Without taints, the scheduler might place any Pod there.

How Add a Taint to the Node

example: kubectl taint nodes worker3 app=database:NoSchedule				

		kubectl:	Kubernetes CLI tool
		taint:		Adds or removes a taint from a node
		nodes:		The resource type (Node)
		worker3:	The node name where the taint will be applied, it will be the hostname of node.
		app=database:	Taint key=app, value=database
		NoSchedule:	Taint effect

If any of the node is tainted, than how we can schedule any pod on that node? :It must include a toleration

apiVersion: v1
kind: Pod
metadata:
  name: mysql
spec:
  tolerations:
  - key: "app"
    operator: "Equal"
    value: "database"
    effect: "NoSchedule"

  containers:
  - name: mysql
    image: mysql

Now the scheduler sees:

Node:
app=database:NoSchedule

Pod:
toleration:
app=database:NoSchedule

✔ Match found

So the Pod can be scheduled onto worker3

Real Use: We can use only specific nodes or machine for specific requirement.


There are three effects you can use:

Effect	Meaning
NoSchedule:			Don't schedule new Pods unless they tolerate the taint. Existing Pods remain running.
PreferNoSchedule:	Try to avoid scheduling Pods here, but it's not a strict rule.
NoExecute:			Evict existing Pods that don't tolerate the taint, and prevent new non-tolerating Pods from being scheduled.

Node Affinity: Node Affinity is a Kubernetes scheduling feature that tells the scheduler which nodes a Pod prefers or 
				is required to run on, based on node labels.

Taints & Tolerations → Control which Pods are allowed onto a node.
Node Affinity → Control which nodes a Pod wants to run on.

Suppose you have three nodes:
worker1
worker2
worker3

Add labels to them
kubectl label nodes worker1 app=frontend
kubectl label nodes worker2 app=backend
kubectl label nodes worker3 app=database

verify
kubectl get nodes --show-labels
output 
worker1   app=frontend
worker2   app=backend
worker3   app=database

Suppose your MySQL Pod should only run on the database node.


Create a Pod with Node Affinity : Suppose your MySQL Pod should only run on the database node.
apiVersion: v1
kind: Pod
metadata:
  name: mysql
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: app
            operator: In
            values:
            - database

  containers:
  - name: mysql
    image: mysql
	
The schedular will check 
worker1
app=frontend
❌ Doesn't match

worker2
app=backend
❌ Doesn't match

worker3
app=database
✔ Matches


Types of Node Affinity
1. Required (Hard Rule) requiredDuringSchedulingIgnoredDuringExecution : The Pod must run on a matching node. If none exists, keep the Pod Pending."
	If no node has:
	app=database
	then STATUS: Pending

	because Kubernetes cannot find a suitable node.
	
2. Preferred (Soft Rule)
	preferredDuringSchedulingIgnoredDuringExecution : "Try to place the Pod on a matching node, but if none is available, schedule it somewhere else."
	
example:
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 100
  preference:
    matchExpressions:
    - key: app
      operator: In
      values:
      - database
	  
		
schedular behaviour
worker1
worker2
worker3  ← preferred

Operators : In, NotIn, Exists, DoesNotExist


Node Affinity + Taints Together : This is a common pattern for dedicated workloads.

first taint the node
kubectl taint nodes worker3 app=database:NoSchedule

Then label the node
kubectl label nodes worker3 app=database

Finally Create the POD
spec:
  tolerations:
  - key: app
    value: database
    effect: NoSchedule

  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: app
            operator: In
            values:
            - database



Difference : Node affinity and Taints

Taint : Node bolta hai "Mere upar koi Pod mat bhejna."
Toleration : Pod bolta hai "Mere paas permission hai. Main is node par aa sakta hoon."Pod gets permission "Main aa sakta hoon."
Node Affinity : Pod bolta hai "Main database node par hi jana chahta hoon.".  Pod chooses "Mujhe kis node par jana hai?"

: it means creating a certificate for a user or component and asking the Kubernetes CA to sign it.

DNS and Core DNS

What is DNS? : It is basically Domain name server, that resolves the IP address into its domain name like 10.164.137.24 -> www.google.com

In kubernetes, every POD gets an IP address, like below
Frontend Pod
10.244.1.10

Backend Pod
10.244.2.15

ANd Pod IPs change frequently. If the frontend tries to connect using: http://10.244.2.15, and the backend pod restarts:
Old IP 10.244.2.15 -> New IP 10.244.3.20
So the communication breaks. SO we need DNS that can resolve IP into hostname. After having DNS change in IPaddress will not break the communication.

Note: We dont have start and stop of PODs, it is only deletion and creation of POD.

Kubernetes Solution : Instead of talking to a Pod IP, the frontend talks to a Service "backend-service".
						The frontend will call "http://backend-service" and DNS will convert it into backend-service -> 10.96.100.20 (which is the ClusterIP of the Service.)
						The Service then forwards traffic to the actual Pod.
						
						The frontend application POD will have endpoint of Backend service. :requests.get("http://backend-service")
						
							Frontend
								│
								▼
							backend-service
								│
								▼
							Backend Pod
	
Note : Each Pod have IP address assigned, and it changes after every recreation.	

CoreDNS: CoreDNS is the DNS server running inside your Kubernetes cluster. Its job is to answer DNS queries. It runs as Pods in the kube-system namespace.
		 Command :kubectl get pods -n kube-system



Fully Qualified Domain Name (FQDN)  : Every Service automatically gets a DNS name. like
Service : backend-service
FQDN : backend-service.default.svc.cluster.local

backend-service → Service name
default → Namespace
svc → Service
cluster.local → Cluster DNS domain

-----------------------------------------Lecture 33  Ingress

Suppose you have 3 applications running in Kubernetes:
Frontend Pod ----> Frontend Service
Backend Pod  ----> Backend Service
Admin Pod    ----> Admin Service

Without Ingress If you expose every Service as a NodePort:
192.168.1.10:30001  → Frontend
192.168.1.10:30002  → Backend
192.168.1.10:30003  → Admin

Problems:
Users have to remember different port numbers.
You expose many ports.
Hard to manage SSL (HTTPS).
Not suitable for production.


*With Ingress Instead, expose only one entry point: The Ingress decides where to send the request.

	
	                Internet
                     |
              www.myapp.com
                     |
              Ingress Controller
                     |
        -----------------------------
        |             |             |
 Frontend Service  Backend Service  Admin Service
        |             |             |
     Frontend Pod   Backend Pod   Admin Pod
	

Example:

***************************************
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress

spec:
  rules:
  - host: myapp.com

    http:
      paths:

      - path: /						//for Example -> Go to Frontend
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80

      - path: /api				//For example -> go to Backend
        pathType: Prefix
        backend:
          service:
            name: backend-service
            port:
              number: 80

      - path: /admin				//For example -> go to admin
        pathType: Prefix
        backend:
          service:
            name: admin-service
            port:
              number: 80
			  
***************************************

Host-based routing : Ingress can also route using different domains.

shop.mycompany.com -> Shopping Service
api.mycompany.com -> API Service
blog.mycompany.com -> Blog Service


Ingress doesn't work alone!: You also need an Ingress Controller.

Example controllers: The Ingress Controller is the software that reads that configuration and actually routes the traffic. Without an Ingress Controller, the Ingress object just sits in Kubernetes and does nothing.

NGINX Ingress Controller
Traefik
HAProxy
AWS Load Balancer Controller
GKE Ingress Controller

Complete Flow
			        Internet
                       |
                  Public IP
                       |
                Load Balancer
                       |
              Ingress Controller
                       |
                  Ingress Rules
          --------------------------
          |            |            |
   Frontend      Backend       Admin
     Service       Service      Service
          |            |            |

Service vs Ingress

| Service                           | Ingress                                  |
| --------------------------------- | ---------------------------------------- |
| Exposes Pods                      | Exposes HTTP/HTTPS applications          |
| Works at Layer 4 (TCP/UDP)        | Works at Layer 7 (HTTP/HTTPS)            |
| Routes to Pods                    | Routes to Services                       |
| One Service per application       | One Ingress can manage many applications |
| Doesn't inspect URLs or hostnames | Can route by URL path and hostname       |
| Doesn't terminate SSL             | Can terminate SSL (HTTPS)                |

Step-By-Step Guide To Upgrade a Multi Node Kubernetes Cluster With Kubeadm

During an upgrade, you upgrade:
✅ kubeadm
✅ Control Plane
✅ kubelet
✅ kubectl (optional but recommended)
✅ Worker Nodes


Upgrade Order
1. Upgrade kubeadm (Control Plane)
           ↓
2. Upgrade Control Plane
           ↓
3. Upgrade kubelet
           ↓
4. Upgrade kubectl
           ↓
5. Upgrade Worker Node 1
           ↓
6. Upgrade Worker Node 2
           ↓
7. Upgrade Worker Node N

Example: Suppose you're upgrading:
v1.34.2
      ↓
v1.35.0


Step 1: Check current version

kubectl get nodes

NAME       VERSION
master     v1.34.2
worker1    v1.34.2
worker2    v1.34.2

Step 2: Upgrade kubeadm : First, install the new kubeadm package.

sudo apt update
sudo apt install kubeadm=1.35.0-1.1
kubeadm version

Step 3: Check upgrade plan
sudo kubeadm upgrade plan

Current Version : v1.34.2
Available:
v1.35.0


Step 4: Upgrade Control Plane
sudo kubeadm upgrade apply v1.35.0


This upgrades:

API Server
Scheduler
Controller Manager
etcd (if needed)
CoreDNS (if applicable)
kube-proxy (if applicable)

It does not upgrade the kubelet binary.


Step 5: Upgrade kubelet
sudo apt install kubelet=1.35.0-1.1
sudo systemctl daemon-reload
sudo systemctl restart kubelet


Step 6: Upgrade kubectl
sudo apt install kubectl=1.35.0-1.1

Step 7: Verify Control Plane
kubectl get nodes

master    Ready   v1.35.0
worker1   Ready   v1.34.2
worker2   Ready   v1.34.2

Only the master is upgraded. Workers are still old.


Step 8: Drain Worker Node : Move all Pods away from worker1.

kubectl drain worker1 --ignore-daemonsets    // Now Kubernetes schedules Pods onto other nodes.

Before Drain						After Drain

worker1								worker1
-------								--------------
Pod A								No Pods
Pod B
Pod C

This prevents downtime during the upgrade.


Step 9: Upgrade kubeadm on Worker
SSH into worker1. and Install

sudo apt install kubeadm=1.35.0-1.1
sudo kubeadm upgrade node

Note: Unlike the control plane, workers use kubeadm upgrade node, not kubeadm upgrade apply.

Step 10: Upgrade kubelet
sudo apt install kubelet=1.35.0-1.1
sudo systemctl daemon-reload
sudo systemctl restart kubelet

Step 11: Uncordon Worker
kubectl uncordon worker1

Step 12: Repeat for Worker 2: Repeat for every worker node.


Final Verification
kubectl get nodes

NAME      VERSION

master    v1.35.0
worker1   v1.35.0
worker2   v1.35.0

Kubernetes ETCD Backup And Restore

etcd is a distributed key-value database that stores the entire state of the Kubernetes cluster.

It stores:

Nodes
Pods
Deployments
Services
ConfigMaps
Secrets
Namespaces
RBAC
Persistent Volumes
...almost everything in the cluster.

Why take an etcd backup? : 
Imagine your control plane server crashes. If there is no backup, all cluster state is lost.
If you have an etcd snapshot, you can restore the cluster to the point when the snapshot was taken.

Taking an etcd Backup
command : ETCDCTL_API=3 etcdctl snapshot save snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
  
  This will create : snapshot.db (This file contains the complete etcd database at that moment.)
  
 
Verify the backup
ETCDCTL_API=3 etcdctl snapshot status snapshot.db

output: 
HASH
REVISION
TOTAL KEYS
TOTAL SIZE

This confirms the snapshot is valid.

Restoring the Backup : command will recreates the etcd data into a new directory: /var/lib/etcd-restore
ETCDCTL_API=3 etcdctl snapshot restore snapshot.db \
  --data-dir=/var/lib/etcd-restore		


Tell Kubernetes to use the restored data: If etcd runs as a static Pod (the default with kubeadm), edit:
Change :  --data-dir=/var/lib/etcd
to 
--data-dir=/var/lib/etcd-restore

The kubelet notices the manifest change and automatically restarts the etcd Pod with the restored data.

OR
kubectl logs mypod -c sidecar

get the real time logs : kubectl logs -f nginx


Centralized Logging In production, you don't SSH into nodes to check logs. Instead, all logs are collected centrally.
Many tools are available to record the logs

CPU Usage

Network Traffic

command : kubectl top nodes				//Check Node Usage

NAME        CPU    MEMORY

master      20%    45%
worker1     40%    60%
worker2     15%    30%

kubectl top pods 				//Check Pod Usage
frontend     120m    250Mi
backend      350m    500Mi
database     900m    2Gi


Where does kubectl top get the data? It gets metrics from the Metrics Server.
